# Lab Development and Structure

Implement the lab (isoloom.yml, build/, provision/) as a realistic app with a single vulnerability; follow structure below.

You are a senior web developer tasked with creating a complete lab described by `isoloom.yml`, with its code in `build/` and `provision/` based on provided files.

Your goal is to **analyze** the template folder, detect the technology stack, adapt to its conventions, and fully implement the scenario as a realistic business application with one vulnerability realistic **following the lab structure below**.

## Directory Naming Convention

The lab directory should have a name that clearly identifies the vulnerability type and is appropriate for the specific vulnerability being demonstrated.

### Examples

- `sql-injection-basic`
- `xss-stored-payload`
- `file-upload-rce`
- `xxe-internal-entities`
- `ssrf-localhost-bypass`
- `ldap-injection-auth-bypass`

### Lab Structure

```
isoloom.yml          # the lab: machines, networks, services, inputs, checks
build/<machine>/     # Docker edition: Dockerfile + src/ (+ init/, evidence scripts)
build/check/check.sh # self-check from the player's side
provision/<machine>.sh  # VM edition of each machine
tests/               # pytest against .isoloom/docker/compose.yml
.isoloom/            # generated by `isoloom generate`, never edited
```

See `DIRECTORY.md` for the full tree and `../run/ISOLOOM.md` for the spec.

### Requirements for the Lab Structure

- Each machine has its folder in `build/` (web, api, database) and its step in `provision/`
- Configuration files live in `build/<machine>/config/`, shared by the Dockerfile and the VM step
- Machine names are lowercase and describe their role
- Must be descriptive of the scenario and easily searchable

## Development Best Practices

### Code Organization

- **Separation of Concerns**: Keep application logic separate from vulnerability code
- **Modular Design**: Use clear module boundaries
- **Configuration Management**: Externalize configuration settings
- **Error Handling**: Implement proper error handling without revealing sensitive information

### Security Considerations

- **Realistic Vulnerabilities**: Create vulnerabilities that mirror real-world scenarios
- **No Obvious Indicators**: Avoid making vulnerabilities too obvious
- **Professional Appearance**: Maintain realistic business application appearance
- **Data Sanitization**: Implement proper input validation where appropriate

### Application Architecture

- **Technology Stack**: Choose appropriate technologies for the vulnerability type
- **Database Design**: Create realistic database schemas
- **API Design**: Implement RESTful APIs where applicable
- **Frontend Integration**: Create professional-looking user interfaces

### File Organization for Build Folder

- **Source Code**: Place application code in service-specific directories (e.g., `web/src/`, `api/src/`)
- **Configuration**: Keep config files in `build/<machine>/config/`
- **Docker Files**: Place Dockerfiles in their machine directories
- **Orchestration**: Only `isoloom.yml`. Never write compose, Vagrant or Terraform files by hand

### Directory Creation Strategy

- **Direct Implementation**: Create the Docker edition in `build/`, the VM edition in `provision/`
- **Service Isolation**: Each service (web, database, api) should have its own subdirectory
- **Flat Structure**: Avoid nested build directories - keep the structure flat and accessible

### Service Organization

- **Web Machines**: Create in `build/web/` with Dockerfile and source code, plus `provision/web.sh`
- **Database Machines**: Create in `build/database/` with initialization scripts, plus `provision/database.sh`
- **API Machines**: Create in `build/api/` with endpoint implementations, plus `provision/api.sh`
- **Configuration**: In each machine's `config/` folder

### Development Workflow

**IMPORTANT**: All steps below are MANDATORY and must be completed. The lab generation is NOT complete until all steps are finished, including the creation of `.ctf/WALKTHROUGH.md`.

1. **Analyze Template**: Understand the existing structure and technology stack
2. **Create Machines**: Build each machine's Docker edition (`build/<machine>/`) and VM edition (`provision/<machine>.sh`)
3. **Describe the Lab**: Write `isoloom.yml` (machines, ports, inputs, evidence volume, checks), run `isoloom generate`, bring it up and run the checks
4. **Implement Vulnerability**: Add realistic security flaws within the application logic
5. **MANDATORY - Create Walkthrough**: You MUST create `.ctf/WALKTHROUGH.md` documenting the complete exploitation path for maintainers/instructors (NOT player-facing). This file is REQUIRED and lab generation is incomplete without it.

## Maintainer Walkthrough Documentation

### Purpose

**MANDATORY**: You MUST create a walkthrough file for maintainers, instructors, and testing purposes. This file is **NOT player-facing** and must be placed in the `.ctf/` directory alongside other generation artifacts. **Lab generation is incomplete without this file.**

### Location

- **File Path**: `.ctf/WALKTHROUGH.md`
- **Directory**: Same level as `SCENARIO.md` and `EVIDENCE.md`
- **Visibility**: Internal/maintainer documentation only (not included in player-facing README)

### Walkthrough Content Requirements

The walkthrough should include:

#### 1. Vulnerability Overview

- Brief description of the vulnerability type
- Location/component where the vulnerability exists
- Why it exists (realistic scenario context)

#### 2. Exploitation Steps

- Step-by-step exploitation path
- Required tools/techniques
- Payloads or attack vectors used
- Expected responses at each step

#### 3. Evidence Extraction

- Exact method to extract the evidence
- Database queries, file paths, API endpoints, or other extraction methods
- Expected evidence form and location (the development value from `EVIDENCE.md`)
- Validation that the extracted data matches the evidence definition in `EVIDENCE.md`

#### 4. Testing and Validation

- How to verify the vulnerability works
- How to test the exploitation path
- Expected results and outputs
- Common issues and troubleshooting

#### 5. Security Context

- Business impact of successful exploitation
- What the evidence represents (admin credentials, sensitive data, etc.)
- Alignment with the scenario's crown jewels

### Walkthrough Structure Example

```markdown
# Vulnerability Walkthrough

## Vulnerability Type

[SQL Injection / XSS / File Upload / etc.]

## Location

[Specific file/endpoint/component where vulnerability exists]

## Exploitation Steps

### Step 1: [Initial Discovery]

- Action: [What to do]
- Expected Result: [What should happen]

### Step 2: [Vulnerability Identification]

- Action: [Test payload or method]
- Expected Result: [Response indicating vulnerability]

### Step 3: [Exploitation]

- Action: [Actual exploit payload]
- Expected Result: [Successful exploitation outcome]

### Step 4: [Evidence Extraction]

- Action: [How to extract the evidence]
- Expected Result: [Evidence value/data]

## Evidence Validation

- Expected Evidence: [Value or location from EVIDENCE.md]
- Extraction Method: [Database query / file read / API call / etc.]
- Validation: [How to verify the extracted data matches the evidence]

## Testing Notes

[Additional information for maintainers to test the lab]
```

### Important Constraints

- **MANDATORY FILE**: The `.ctf/WALKTHROUGH.md` file MUST be created during lab generation. Do not skip this step.
- **NOT Player-Facing**: This walkthrough must NOT be referenced in player-facing documentation (README.md, UI, etc.)
- **Maintainer Use Only**: Intended for lab creators, reviewers, and instructors
- **Detailed Enough**: Should enable a maintainer to reproduce the exploitation without guessing
- **Matches EVIDENCE.md**: The extraction method must align with the evidence definition in `.ctf/EVIDENCE.md`
- **No Spoilers in Player Docs**: Ensure README.md and other player-facing content do not reference this walkthrough
