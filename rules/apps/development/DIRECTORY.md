# Directory Structure

Canonical lab directory layout: where the spec, code, VM steps, checks, tests and metadata live.

Same layout as the reference lab `github.com/CyberCTF/invoice-portal-api`.

```
<lab-slug>/
├── isoloom.yml                    # The lab: machines, networks, services, inputs, checks
├── .isoloom/                      # Generated by `isoloom generate`; committed, never edited
│   ├── docker/compose.yml         # Containers (pytest and CI use this)
│   ├── vagrant/Vagrantfile        # One VM per machine
│   ├── docker-vm/                 # Docker on one VM (Vagrantfile, proxmox/main.tf)
│   ├── proxmox/main.tf            # One VM per machine on Proxmox
│   └── cloud-docker/<cloud>/main.tf
├── build/                         # Docker edition: one folder per machine
│   ├── web/
│   │   ├── Dockerfile
│   │   └── src/                   # Application code (also used by the VM edition)
│   ├── database/
│   │   ├── Dockerfile             # COPY init/ and the evidence scripts
│   │   ├── init/                  # 01-*.sql, 02-*.sql, ...
│   │   ├── claim-evidence.sh      # From the template, unchanged
│   │   ├── place-evidence.sh      # Lab-specific placement
│   │   └── evidence.sh            # docker.init job: claim, then place
│   └── check/
│       └── check.sh               # `checks:` script: the lab is still solvable
├── provision/                     # VM edition: one step per machine
│   ├── web.sh
│   └── database.sh
├── tests/                         # pytest, against .isoloom/docker/compose.yml
│   ├── conftest.py
│   ├── requirements.txt
│   └── test_lab.py
├── .github/workflows/
│   ├── validate.yml               # isoloom validate/check, lab up + checks, terraform, vagrant
│   └── publish.yml                # Registers the lab with CyberCTF from .ctf/metadata.json
├── README.md                      # Player-facing, per the README template
└── .ctf/                          # Generation artefacts and metadata
    ├── SCENARIO.md
    ├── EVIDENCE.md
    ├── WALKTHROUGH.md
    ├── metadata.json
    ├── test_results/
    └── timing_logs/
```

There is no `docker-compose.yml`, no `build/docker-compose.dev.yml` and no `deploy/` folder.

## Naming

- Lab slug (repo name and `name:` in `isoloom.yml`): kebab-case, describes the scenario
  (e.g. `invoice-portal-api`, `sql-injection-basic`).
- Machine names: lowercase DNS labels, describe the role: `web`, `api`, `database`, `auth`,
  `admin`, `cache`. The `build/<machine>/` and `provision/<machine>.sh` names match.

## Machine folders

```
build/<machine>/
├── Dockerfile                     # Required for `docker: { build: build/<machine> }`
├── src/                           # Application code, if any
└── config/                        # Server configs COPY'd into the image and reused by the VM step
```

- A machine that only uses a published image (`docker: { image: redis:7 }`) needs no folder,
  unless it has `init` scripts.
- Keep configs in files under `build/<machine>/config/`, so the Dockerfile and the VM step use
  the same file.

## Best practices

1. Source code in `build/<machine>/src/`, shared by both editions.
2. One Dockerfile per machine, one provision step per machine.
3. Numbered SQL files in `build/database/init/`.
4. Tests in `tests/`, organised by type.
5. All generation artefacts in `.ctf/`.
